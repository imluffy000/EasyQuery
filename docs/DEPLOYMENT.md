# Deploying to Render + Supabase + Upstash

Three managed services, one blueprint:

| Piece | Provider | What it is |
| ----- | -------- | ---------- |
| API | Render web service (Docker) | FastAPI behind gunicorn/uvicorn |
| Web | Render static site | the Vite bundle on Render's CDN |
| Control-plane database | Supabase Postgres | users, workspaces, saved connections, query history |
| Redis | Upstash | rate-limiter counters |

The customer databases the copilot *queries* are not part of this: users add
those through the app at runtime.

`render.yaml` in the repo root declares both Render services. Every secret is
marked `sync: false` or `generateValue: true`, so nothing sensitive is
committed — Render prompts for the rest on first apply.

---

## 1. Supabase

1. Create a project. Save the database password it generates.
2. **Connect** (top of the dashboard) → **Connection pooling** → copy the
   **Transaction pooler** URI. It looks like:

   ```
   postgresql://postgres.<project-ref>:<password>@aws-0-<region>.pooler.supabase.com:6543/postgres
   ```

3. Append `?sslmode=require`, and substitute the real password.

Two things here are not optional:

**Use the pooler, not the direct connection.** Supabase's direct host
(`db.<ref>.supabase.co:5432`) resolves to IPv6 only. Render services are
IPv4-only, so a direct DSN cannot connect at all. The pooler is dual-stack.

**Port 6543, transaction mode, is what the app expects.** The application
detects port `6543` (or an explicit `?pgbouncer=true`) and reacts by disabling
both asyncpg statement caches and dropping its own connection pool in favour of
NullPool — see `uses_transaction_pooler` in
[session.py](../backend/app/database/session.py). Without that, a transaction
pooler hands consecutive statements to different server connections and you get
intermittent `prepared statement "__asyncpg_stmt_3__" does not exist` failures
under load. Session mode (port 5432 on the pooler host) also works and keeps
statement caching; it just holds one server connection per client.

If the password contains `@`, `:`, `/`, `#` or `?`, percent-encode it or reset
it to something alphanumeric. Those characters are DSN syntax.

No extensions or SQL need running by hand. Primary keys are UUIDs generated in
Python, and the schema is created by Alembic on the first deploy.

## 2. Upstash

1. Create a Redis database. Pick the region closest to the Render region
   (`oregon` in the blueprint → `us-west-1`).
2. Copy the **`rediss://` TCP URL**, not the REST URL:

   ```
   rediss://default:<password>@<name>-<id>.upstash.io:6379
   ```

   The REST/HTTP endpoint (`https://...upstash.io`) is a different protocol and
   `RedisDsn` validation rejects it at start-up.

`rediss://` (two s's) is TLS, which Upstash requires. Redis holds only
fixed-window rate-limit counters with a 90-second TTL, so the free tier is
ample and no eviction tuning is needed. If Redis is unreachable the API stays
up and the limiter fails open — it logs `redis_unavailable` and keeps serving.

## 3. Render

### First pass — create the services

1. **New → Blueprint**, pick the `imluffy000/EasyQuery` repo, branch `main`.
2. Render reads `render.yaml` and asks for each `sync: false` value:

   | Variable | Value |
   | -------- | ----- |
   | `DATABASE_URL` | the Supabase transaction-pooler URI from step 1 |
   | `REDIS_URL` | the Upstash `rediss://` URL from step 2 |
   | `LLM_PROVIDER` | `anthropic`, `openai`, `openrouter`, or `echo` |
   | `LLM_MODEL` | the provider's own naming — `claude-sonnet-5`, `gpt-4o`, `anthropic/claude-sonnet-4.5` |
   | `LLM_API_KEY` | the key for that provider (may be blank only if `echo`) |
   | `CORS_ORIGINS` | placeholder for now — see below |
   | `FRONTEND_URL` | placeholder for now |
   | `VITE_API_URL` | placeholder for now |

   `ENCRYPTION_KEY` and `JWT_SECRET` are generated by Render and never leave it.

3. Apply. The first backend deploy builds the Docker image, runs
   `alembic upgrade head`, then starts gunicorn.

Those three URL variables are a chicken-and-egg: their values are the URLs
Render is about to assign. Put anything syntactically valid in on the first
pass (`https://example.com`) and correct them in the second.

### Second pass — wire the URLs together

Once both services exist, copy their real URLs from the dashboard. Render uses
`https://<service-name>.onrender.com`, with a random suffix appended when the
name was already taken globally — so read them rather than assuming them.

On **easyquery-api** → Environment:

| Variable | Value |
| -------- | ----- |
| `CORS_ORIGINS` | `https://easyquery-web.onrender.com` |
| `FRONTEND_URL` | `https://easyquery-web.onrender.com` |

On **easyquery-web** → Environment:

| Variable | Value |
| -------- | ----- |
| `VITE_API_URL` | `https://easyquery-api.onrender.com/api/v1` |

No trailing slashes, and `CORS_ORIGINS` must be the static site's scheme + host
exactly — a wildcard is rejected at start-up when `APP_ENV=production`.

`VITE_API_URL` is compiled into the JavaScript bundle, so changing it needs a
**rebuild** of the static site ("Clear build cache & deploy"), not a restart.
The backend picks its own changes up on a plain restart.

### Optional — social sign-in

Google and GitHub OAuth stay off unless configured. Add these to
**easyquery-api**, and register the same callback URLs with each provider:

```
GOOGLE_CLIENT_ID, GOOGLE_CLIENT_SECRET
GOOGLE_CALLBACK_URL=https://easyquery-api.onrender.com/api/v1/auth/oauth/google/callback
GITHUB_CLIENT_ID, GITHUB_CLIENT_SECRET
GITHUB_CALLBACK_URL=https://easyquery-api.onrender.com/api/v1/auth/oauth/github/callback
```

`ADMIN_EMAIL` promotes exactly that email to superuser on its next login.

## Verifying the deploy

```bash
curl https://easyquery-api.onrender.com/api/v1/health
# {"status":"ok","version":"0.1.0","environment":"production"}

curl https://easyquery-api.onrender.com/api/v1/ready
# {"status":"ready","checks":{"postgres":true,"redis":true,"llm":true}}
```

`/ready` is the one that proves Supabase and Upstash are both reachable. Note
that Render's health check points at `/health`, which deliberately touches no
dependency: aiming it at `/ready` would pull the whole service out of rotation
over a momentarily degraded rate limiter.

Then open the static site, register an account, and connect a database.

## Operational notes

- **Migrations run at container start**, not in a pre-deploy hook, because the
  free and starter plans do not have one. Alembic locks its version table, so
  concurrent instances are safe: the first migrates, the rest find nothing to
  do. `RUN_MIGRATIONS=false` disables it.
- **`WEB_CONCURRENCY=2`** on a 512MB starter instance. Each uvicorn worker
  loads the LangGraph pipeline; four workers get OOM-killed mid-request, which
  surfaces as a 502 with nothing in the application log.
- **Never regenerate `ENCRYPTION_KEY`.** It decrypts the stored customer
  database passwords. Rotating it without re-encrypting makes every saved
  connection unreadable. `SecretBox.from_keys([new, old])` supports a real
  rotation.
- **`/docs` and `/openapi.json` are disabled** when `APP_ENV=production`.
  `/metrics` stays open — put it behind Render's IP allowlist or a proxy if that
  matters to you.
- **The `free` plan sleeps** after 15 idle minutes, and the next request waits
  for a container start *and* a migration check. Starter avoids that.
- **The seeded `demo_analytics` database is local-only** — it comes from
  `infra/postgres`, which only docker-compose mounts. In production, users
  connect their own databases.
- **Prometheus, Grafana and the OTel collector are not deployed.** They are
  compose-only; `OTEL_ENDPOINT` is left unset in production, and tracing is not
  wired into `main.py` in any case.
